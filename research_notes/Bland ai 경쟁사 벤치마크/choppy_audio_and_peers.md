# Choppy audio in Twilio Media Streams ↔ OpenAI Realtime bridges, and how the platforms avoid it

Researcher notes, 2026-09-29. Scope: (1) root causes and proven fixes for choppy / cutting-out / stuttering audio in a Twilio-Media-Streams ↔ OpenAI-Realtime bridge; (2) how Bland, Vapi, Retell, LiveKit, Pipecat, ElevenLabs, Twilio ConversationRelay (and OpenAI's own SIP connector) architect their audio path; (3) real-world reports on Bland's audio quality/latency/reliability and per-minute pricing across options.

Conventions used below: **[DOC]** = primary vendor documentation or source code; **[ISSUE]** = a public issue/forum thread (anecdotal but concrete, usually with numbers); **[VENDOR-BLOG]** = a competitor- or vendor-authored comparison (treat numbers as claims); **[3P]** = third-party blog/aggregator. Anything pre-dating the `gpt-realtime` GA (2025-08-28) is flagged "pre-GA".

## Key question 1 — Twilio Media Streams mechanics (framing, buffering, `media`/`mark`/`clear`)

### Takeaway
Twilio's bidirectional stream is a simple base64-mulaw-over-WebSocket pipe: Twilio *buffers everything you send and plays it in order*, echoes a `mark` when each marked chunk has finished playing, and only stops playing already-sent audio if you send `clear`. Twilio documents no frame-size, rate, or buffer-depth limits, which is exactly why bridges that push audio faster than real time (fine for playback, fatal for barge-in) or slower than real time (audible warble/clipping) misbehave without any error from Twilio.

### Cited Findings
- Twilio sends `connected`, `start`, `media`, `dtmf`, `stop`, and (bidirectional only) `mark` events; your server may send only `media`, `mark`, and `clear`. "For bidirectional Streams, Twilio only accepts the documented media, mark, and clear message types" — any other message triggers error 31951 "Stream - Protocol - Invalid Message". — [Twilio Media Streams WebSocket messages [DOC]](https://www.twilio.com/docs/voice/media-streams/websocket-messages); [Twilio error 31951 [DOC]](https://www.twilio.com/docs/api/errors/31951)
- Inbound `media` payload metadata: encoding "is always audio/x-mulaw", sample rate "is always 8000", channels "is always 1"; each `media` carries `track` ("inbound or outbound"), a sequential `chunk` counter starting at 1, and `timestamp` = "Presentation Timestamp in Milliseconds from the start of the stream". — [Twilio WebSocket messages [DOC]](https://www.twilio.com/docs/voice/media-streams/websocket-messages)
- Outbound audio you send "must be encoded as audio/x-mulaw with a sample rate of 8000 and base64 encoded"; "The media messages are buffered and played in the order received." — [Twilio WebSocket messages [DOC]](https://www.twilio.com/docs/voice/media-streams/websocket-messages)
- `mark`: "When your server sends a media message, it should then send a mark message... When that media message's playback is complete, Twilio sends a mark message to your server using the same mark.name"; Twilio also echoes the mark "if there is no audio buffered". — [Twilio WebSocket messages [DOC]](https://www.twilio.com/docs/voice/media-streams/websocket-messages)
- `clear`: "Send a clear message if you want to interrupt the audio that has been sent in various media messages. This empties all buffered audio" and "Twilio empties the audio buffer and sends back mark messages matching any remaining mark messages from your server". — [Twilio WebSocket messages [DOC]](https://www.twilio.com/docs/voice/media-streams/websocket-messages)
- Every message references `streamSid`, "The unique identifier of the Stream"; it arrives in the `start` event and must be echoed in every outbound `media`/`mark`/`clear`. — [Twilio WebSocket messages [DOC]](https://www.twilio.com/docs/voice/media-streams/websocket-messages)
- **No documented limits**: the WebSocket-messages page states nothing about chunk size, message rate, maximum buffered seconds, or a "one message per 20 ms" rule (my fetch of the page confirmed the absence). — [Twilio WebSocket messages [DOC]](https://www.twilio.com/docs/voice/media-streams/websocket-messages)
- `<Connect><Stream>` (bidirectional) blocks the TwiML: "Twilio doesn't execute subsequent TwiML instructions until your server closes the WebSocket"; bidirectional streams can only receive `inbound_track`; URL must be `wss://`, query strings unsupported (use `<Parameter>`, name+value < 500 chars); `statusCallback` fires on stream start/stop/error with `StreamSid`, `StreamEvent`, error details. — [Twilio `<Stream>` TwiML [DOC]](https://www.twilio.com/docs/voice/twiml/stream)
- Twilio's own Realtime sample forwards each OpenAI `response.output_audio.delta` to Twilio **immediately with no pacing** (`await websocket.send_json(audio_delta)`), records `response_start_timestamp_twilio = latest_media_timestamp` when a new assistant item starts, sends a `mark` per response, and on `input_audio_buffer.speech_started` computes `elapsed_time = latest_media_timestamp - response_start_timestamp_twilio`, sends `conversation.item.truncate {audio_end_ms: elapsed_time}` and a Twilio `{"event":"clear"}`. It configures `audio.input/output.format.type = "audio/pcmu"` and `turn_detection: {type: "server_vad"}`. — [twilio-samples/speech-assistant-openai-realtime-api-python main.py [DOC/code]](https://github.com/twilio-samples/speech-assistant-openai-realtime-api-python/blob/main/main.py)
- The "faster than real time" failure mode is documented in an SDK bug: in `openai-agents-js`'s Twilio transport, "If generation and submission to Twilio takes 1 second but the actual response is 10 seconds long, users only have a 1-second window to interrupt successfully" because the interrupt path stops sending `clear` once the OpenAI response is fully generated; the fix is to always send Twilio `clear` on interrupt "even after OpenAI finishes generating". — [openai/openai-agents-js issue #1173, opened 2026-04-15 [ISSUE]](https://github.com/openai/openai-agents-js/issues/1173)
- The "slower than real time" failure mode is measured in an OpenClaw bug: a pacer that used relative `setTimeout(20)` drifted "+3,368 ms over 35.59 s (+9.48%)", mean interval 21.896 ms, 60 intervals > 25 ms and 12 > 40 ms; "Accumulated underfeed triggers Twilio's jitter-buffer concealment" heard as "clipping/warble/time distortion". Rewriting to monotonic deadlines (`performance.now()`, `nextSendDeadlineMs`, reset on drain/clear/stall > 100 ms) gave "+5 ms drift over 34.20 s (+0.015%)", mean 20.003 ms. Issue closed 2026-08-04, P1. — [openclaw/openclaw issue #119070 [ISSUE]](https://github.com/openclaw/openclaw/issues/119070)
- Pipecat's Twilio serializer converts PCM→μ-law (`pcm_to_ulaw(data, frame.sample_rate, self._twilio_sample_rate)`), base64s it into `{"event":"media","streamSid":...,"media":{"payload":...}}`, and on an `InterruptionFrame` sends `{"event":"clear","streamSid":...}`; it does **not** use `mark`. — [Pipecat `serializers/twilio.py` source [DOC/code]](https://reference-server.pipecat.ai/en/latest/_modules/pipecat/serializers/twilio.html)

### Inferences
- Frame arithmetic (derived from the documented 8 kHz, 8-bit mono μ-law): 8,000 bytes/s → **160 bytes per 20 ms**, 400 bytes per 50 ms, 8 bytes per ms. `timestamp` on inbound `media` is therefore a reliable wall-clock for the caller side, and `chunk` gaps reveal Twilio-side loss.
- Because Twilio buffers without limit and plays in order, *sending faster than real time never causes choppiness by itself*; it causes (a) a large playout backlog that only `clear` can discard, and (b) `mark` echoes and truncation offsets that are far from what the caller has heard (see KQ2/KQ3). Conversely, *any interval where your send rate falls below 8 kB/s while Twilio's buffer is empty* is an underrun that Twilio conceals audibly — this is the mechanism behind "warble/clipping" in the OpenClaw measurement.
- The correct design that the measured fixes converge on: (1) an outbound queue fed by OpenAI deltas, (2) a 20 ms-per-frame sender driven by a monotonic deadline (not a relative sleep), (3) a small pre-roll (≈100–200 ms) before the first frame of each response so burst gaps don't underrun, (4) `clear` + queue flush on barge-in, (5) `mark` per response (or per N frames) to know what has actually played.

### Gaps
- Twilio does not publish the depth of its outbound playout buffer, its jitter-buffer/concealment algorithm, or the maximum backlog it will accept; no source found.
- No Twilio document states a "one media message per 20 ms" recommendation; the 20 ms cadence is convention observed in inbound frames and in the community fixes, not a documented requirement.

## Key question 2 — OpenAI Realtime API specifics (formats, VAD, interruption, limits, known artifacts, GA changes)

### Takeaway
OpenAI accepts/emits 8 kHz G.711 μ-law natively (`audio/pcmu` post-GA, `g711_ulaw` pre-GA), so no transcoding is needed with Twilio; audio arrives in bursts of `response.output_audio.delta`, sessions are capped at 60 minutes, and interruptions must be handled by the client (`speech_started` → stop playback → `conversation.item.truncate` with the *played* ms). The persistent OpenAI-side defects reported by developers are (a) the last 0.5–1 s of audio occasionally never being sent (2024–Jan 2025, preview models), and (b) latency blow-ups when `input_audio_noise_reduction` is combined with `semantic_vad` or transcription (May 2025, preview model); no confirmed OpenAI fix found for either.

### Cited Findings
- Formats: the GA docs show `"audio": {"input": {"format": {"type": "audio/pcm", "rate": 24000}}}` and the μ-law variant `"type": "audio/pcmu"` for output; the Twilio sample uses `audio/pcmu` for both directions. Pre-GA code used `input_audio_format: "g711_ulaw"`. — [OpenAI Realtime conversations guide [DOC]](https://developers.openai.com/api/docs/guides/realtime-conversations); [Twilio sample main.py [DOC/code]](https://github.com/twilio-samples/speech-assistant-openai-realtime-api-python/blob/main/main.py)
- "To get the actual bytes, you'll need to listen for the `response.output_audio.delta` events" (Base64 chunks); "The maximum duration of a Realtime session is 60 minutes." — [OpenAI Realtime conversations guide [DOC]](https://developers.openai.com/api/docs/guides/realtime-conversations)
- Interruptions: on `input_audio_buffer.speech_started` "the client... should immediately stop playback of any audio currently being played from the model"; then send `conversation.item.truncate {item_id, content_index: 0, audio_end_ms}`; `response.cancel` aborts an in-progress response; `output_audio_buffer.clear` exists for WebRTC. — [OpenAI Realtime conversations guide [DOC]](https://developers.openai.com/api/docs/guides/realtime-conversations)
- VAD: `server_vad` params `threshold` ("0 to 1. A higher threshold will require louder audio to activate the model, and thus might perform better in noisy environments"), `prefix_padding_ms`, `silence_duration_ms` ("With shorter values turns will be detected more quickly"), plus `create_response` and `interrupt_response` (conversation mode only). `semantic_vad` has `eagerness` = `low|medium|high|auto`, "'auto' is the default value, and is equivalent to 'medium'". The guide page lists no numeric defaults. — [OpenAI Realtime VAD guide [DOC]](https://developers.openai.com/api/docs/guides/realtime-vad)
- Noise reduction: `input_audio_noise_reduction` "filters audio added to the input audio buffer before it is sent to VAD and the model... can improve VAD and turn detection accuracy (reducing false positives)"; types `near_field` ("close-talking microphones such as headphones") and `far_field` ("laptop or conference room microphones"); absent = off. — [OpenAI Realtime session schema as mirrored in LangChain typings [DOC-mirror]](https://v03.api.js.langchain.com/interfaces/_langchain_openai.OpenAIClient.Beta.Realtime.Sessions.Session.InputAudioNoiseReduction.html)
- Noise-reduction latency bug (pre-GA): with `semantic_vad (eagerness: high)` + `input_audio_noise_reduction: near_field` + `whisper-1` transcription on `gpt-4o-realtime-preview-2024-12-17`, "approximately 5 minutes into a conversation" latency between speech stop and `speech_started` grew "up to a full minute"; removing noise reduction resolved it; reproducible in OpenAI's own console; no OpenAI fix in thread (2025-05-09). — [OpenAI community thread 1256390 [ISSUE, pre-GA]](https://community.openai.com/t/realtime-api-with-noise-reduction-has-sudden-increase-of-latency/1256390)
- Audio-truncated-at-end bug (pre-GA): responses "cutting the final 0.5–1 seconds" while transcript is complete; frequency "approximately every 5th request" up to "5–10% of messages", some "up to 50% of initial audio responses"; theories (content filter, SDK race between `response.audio.done`/`content_part.done`, server buffer) all contradicted; one OpenAI staffer said "looking into this now" (2024-11-05) with no follow-up; no workaround. — [OpenAI community thread 980587 (2024-10-15 → 2024-11-08) [ISSUE, pre-GA]](https://community.openai.com/t/realtime-api-audio-is-randomly-cutting-off-at-the-end/980587)
- Same symptom re-reported 2025-01-17 with event logs: `response.audio.delta` "stop prematurely before the final `response.audio.done`", token counts match the full audio "suggesting packets were generated server-side but never transmitted"; ~1 in 20 responses; no resolution. — [OpenAI community thread 1094267 [ISSUE, pre-GA]](https://community.openai.com/t/websocket-realtime-api-randomly-dropping-audio-packets/1094267)
- Truncation-timeline mismatch on Twilio: `audio_end_ms` computed from the bridge's clock truncates "at the wrong point"; "transcript deltas continue to arrive for audio that was never played"; the poster followed Twilio's official example and "the issue still persists" (Jan 2026); recommended approach is to anchor on Twilio `mark` echoes so only acknowledged playback is treated as heard. — [OpenAI community thread 1371637 [ISSUE]](https://community.openai.com/t/openai-realtime-how-to-correctly-truncate-a-live-streaming-conversation-on-speech-interruption-twilio-media-streams/1371637)
- Carrier-dependent silence: with Austria's A1, the bridge received "only speech (partial audio)" rather than continuous audio including silence, and Realtime performance degraded; options considered were injecting artificial silence or changing VAD settings (2025-01-22, `server_vad`). — [OpenAI community thread 1098589 [ISSUE, pre-GA]](https://community.openai.com/t/openai-realtime-api-full-audio-including-silence-vs-partial-audio-twilio-integration/1098589)
- Bursty delivery: "OpenAI's realtime audio arrives in bursts, and Twilio expects steady pacing" (community member domgeldart, 2025-12-23), fix = deque + separate receive/send tasks + `asyncio.sleep(0.02)` pacing; OP did not confirm. — [OpenAI community thread 1369994 "Realtime-Twilio Jittery Voice" (2025-12-22) [ISSUE]](https://community.openai.com/t/realtime-twillio-jittery-voice/1369994)
- `gpt-realtime` GA (2025-08-28): "more advanced speech-to-speech model with new API capabilities including MCP server support, image input, and SIP phone calling support"; "trained to produce higher-quality speech that sounds more natural"; new voices Marin and Cedar, existing eight voices updated. — [OpenAI "Introducing gpt-realtime" [DOC]](https://openai.com/index/introducing-gpt-realtime); [heise retrospective [3P]](https://www.heise.de/en/background/OpenAI-Realtime-API-What-has-happened-in-the-year-since-the-beta-11170104.html)
- OpenAI SIP connector (GA-era): point a SIP trunk at `sip:$PROJECT_ID@sip.api.openai.com;transport=tls` (EU: `sip-eu.api.openai.com`), TLS port 5061; incoming call → `realtime.call.incoming` webhook → Accept/Reject(e.g. 486)/Refer/Hang-up endpoints; "The WebSocket behaves exactly like any other Realtime API connection" but the app receives **events, not audio**; endpoints are "GeoIP-routed"; media is SRTP over UDP. The same page notes "GPT-Live supports raw G.711 μ-law and A-law audio at 8 kHz over WebSocket." — [OpenAI Realtime SIP guide [DOC]](https://developers.openai.com/api/docs/guides/realtime-sip); [Twilio tutorial: Elastic SIP Trunking → OpenAI SIP [DOC]](https://www.twilio.com/en-us/blog/developers/tutorials/product/openai-realtime-api-elastic-sip-trunking)
- Pricing (third-party, citing OpenAI, July 2026): `gpt-realtime-2.1` $32/1M audio-input tokens, $0.40/1M cached audio input, $64/1M audio-output tokens; "Every minute the assistant speaks bills 1,200 tokens × $64 / 1M = $0.077"; realistic "$0.06–0.11/min flagship once caching works"; `gpt-realtime-2.1-mini` $10/$0.30/$20 per 1M. OpenAI's own pricing page returned 403 to my fetch. — [Forasoft "OpenAI Realtime API pricing" [3P]](https://www.forasoft.com/blog/article/openai-realtime-api-pricing); [eesel gpt-realtime-mini pricing [3P]](https://www.eesel.ai/blog/gpt-realtime-mini-pricing)

### Inferences
- With `audio/pcmu` on both sides the bridge is a pure relay (no resampling/transcoding), so any CPU cost in the bridge is JSON + base64 only; "mulaw transcoding" is not a plausible cause of choppiness in this stack (it is in Pipecat/LiveKit paths that run 16–24 kHz PCM internally).
- The truncation bug and the interrupt-window bug have the same root: the bridge's notion of "what has played" is the OpenAI generation clock, not Twilio's playout clock. Using Twilio's inbound `media.timestamp` as the clock (as Twilio's sample does) is only accurate if outbound audio is paced at real time and started with a known pre-roll; otherwise `mark` echoes are the only ground truth.
- The two OpenAI-side artifact reports (end-of-audio drop, noise-reduction latency) are all on `gpt-4o-realtime-preview` models; I found no equivalent threads against `gpt-realtime` GA, which is weak evidence that GA improved them but not proof.

### Gaps
- Numeric defaults for `server_vad` (`threshold`, `prefix_padding_ms`, `silence_duration_ms`) and `idle_timeout_ms`: the VAD guide omits them and the API-reference page 404'd; do not assume values.
- `response.output_audio.delta` chunk size: no OpenAI document states it; the only datapoint is the openai-agents-python PR describing outgoing chunks of "20–60 bytes" (pre-batching) in μ-law, i.e. 2.5–7.5 ms of audio per delta — anecdotal.
- OpenAI rate limits for Realtime sessions/concurrency: not found in fetched docs.
- Any 2026 OpenAI changelog entry specifically about telephony audio-quality fixes: not found (third-party posts mention "gpt-realtime-2" in May 2026 but I could not verify on openai.com).

## Key question 3 — Root-cause catalogue for intermittent choppy audio (prioritized, with evidence grade)

### Takeaway
Ordered by how often the evidence points at each: (1) outbound pacing/underrun in the bridge, (2) barge-in not clearing Twilio's buffer or clearing at the wrong time, (3) truncation-clock mismatch, (4) network/region distance and jitter on the Twilio↔bridge leg, (5) VAD misfires from phone noise/echo, (6) OpenAI-side artifacts (pre-GA), (7) event-loop starvation. Items 1–3 have measured, reproducible fixes; 4–5 have documented knobs; 6 has no fix; 7 is widely asserted but I found no primary measurement for a Twilio+Realtime bridge specifically.

### Cited Findings
1. **Bursty forwarding / pacing drift (P1).** Symptom "jittering/skip sounds at the beginning of every word... choppy and robotic"; cause "outgoing audio (OpenAI→Twilio) sent tiny 20–60 byte chunks immediately without accumulation"; fix batched to ≥400 bytes (50 ms @ 8 kHz) with a 100 ms periodic flush and aggregated `mark`s — but the PR was **closed unmerged 2025-12-21 after the reporter still heard jitter**. — [openai-agents-python PR #1926 [ISSUE]](https://github.com/openai/openai-agents-python/pull/1926). Independently, the measured 20 ms deadline-scheduled pacer fix (drift 9.48% → 0.015%) eliminated warble. — [openclaw #119070 [ISSUE]](https://github.com/openclaw/openclaw/issues/119070). Community fix: deque + 20 ms `asyncio.sleep` pacing. — [OpenAI thread 1369994 [ISSUE]](https://community.openai.com/t/realtime-twillio-jittery-voice/1369994)
2. **Barge-in without `clear`, or `clear` skipped once generation finished (P1).** Documented in [openai-agents-js #1173 [ISSUE]](https://github.com/openai/openai-agents-js/issues/1173); Twilio's `clear` semantics in [Twilio docs [DOC]](https://www.twilio.com/docs/voice/media-streams/websocket-messages); Pipecat sends `clear` on every `InterruptionFrame` [Pipecat source [DOC]](https://reference-server.pipecat.ai/en/latest/_modules/pipecat/serializers/twilio.html).
3. **Truncation offset computed on the wrong clock (P1).** [OpenAI thread 1371637 [ISSUE]](https://community.openai.com/t/openai-realtime-how-to-correctly-truncate-a-live-streaming-conversation-on-speech-interruption-twilio-media-streams/1371637); Twilio sample's `latest_media_timestamp` approach [Twilio sample [DOC/code]](https://github.com/twilio-samples/speech-assistant-openai-realtime-api-python/blob/main/main.py).
4. **Region / network leg (P2).** Twilio "only has 3 processing regions: US1 (United States), IE1 (Ireland), and AU1 (Australia), and by default, all calls and messages are routed to US1" (Vapi support thread quoting Twilio). — [Vapi support "Large Variance in Delays Web VS Call" [ISSUE]](https://support.vapi.ai/t/33262156/large-variance-in-delays-web-vs-call). Twilio: "the chosen Edge Location directly influences media latency and call quality"; servers "can minimize latency by connecting to the nearest Edge Location". — [Twilio Understanding Edge Locations [DOC]](https://www.twilio.com/docs/global-infrastructure/understanding-edge-locations). Measured transport-only latency Twilio (Ashburn) ↔ LiveKit agent, same US region: "325 ms round-trip (approximately 162 ms one-way)". — [LiveKit community thread 270 (2026-02-09) [ISSUE]](https://community.livekit.io/t/subject-325ms-one-way-audio-latency-in-sip-inbound-trunk-need-internal-pipeline-diagnostics/270). Multi-region deployment claimed to save "60–250 ms travel delays". — [Hamming.ai (2026-01-12) [3P]](https://hamming.ai/blog/voice-ai-latency-whats-fast-whats-slow-how-to-fix-it). Pipecat exposes `region` ("au1", "ie1") and `edge` ("sydney", "dublin") on its Twilio serializer. — [Pipecat Twilio serializer docs [DOC]](https://docs.pipecat.ai/api-reference/server/services/serializers/twilio.md)
5. **Self-hosted host / network problems that look like software bugs (P2).** LiveKit self-hosted on AWS: "glitches, crackly noise, chopping, and intermittent voice dropout" on SIP/Twilio only, WebRTC fine; diagnostics showed "106 restarts, 1,434 mix jumps, 717 zero-mix events" in the SIP mixer; advice: PCAP "jitter, loss and delta", not config changes (2026-04-27). — [LiveKit community thread 957 [ISSUE]](https://community.livekit.io/t/glitches-crickly-noise-chopping-some-time-voice-goes-away/957)
6. **VAD misfires / false barge-in from phone noise and echo (P2).** OpenAI: raise `threshold` for noisy environments [OpenAI VAD guide [DOC]](https://developers.openai.com/api/docs/guides/realtime-vad); LiveKit's telephony example uses OpenAI Realtime `threshold=0.7` "for noisy phone audio" [LiveKit turns docs [DOC]](https://docs.livekit.io/agents/build/turns/); Vapi users: "Default endpointing (200ms) causes false interruptions on mobile networks... increase to 300–400ms" [Vapi community, via search summary [ISSUE]](https://support.vapi.ai/t/23142402/vapi-stops-at-the-very-slight-noise-in-the-background); Retell recommends `interruption_sensitivity` 0.8 for noisy environments and offers a "Remove noise + background speech" (BVC) mode at $0.005/min [Retell docs [DOC]](https://docs.retellai.com/build/handle-background-noise.md); Bland ships `noise_cancellation` default `true` and `interruptibility` 0–3 (default 2) [Bland API docs [DOC]](https://docs.bland.ai/api-v1/post/calls). Background-noise and poor-recognition threads on OpenAI's forum for phone audio: [1103627 [ISSUE]](https://community.openai.com/t/background-noise-interfering-with-realtime-api-using-phone/1103627), [1093045 [ISSUE]](https://community.openai.com/t/realtime-api-poor-speech-recognition-twilio-openai/1093045).
7. **OpenAI-side end-of-response audio drop (P3, pre-GA, no fix).** [thread 980587](https://community.openai.com/t/realtime-api-audio-is-randomly-cutting-off-at-the-end/980587), [thread 1094267](https://community.openai.com/t/websocket-realtime-api-randomly-dropping-audio-packets/1094267), [thread 1002185](https://community.openai.com/t/issue-with-realtime-api-voice-cutting-itself-off/1002185).
8. **Noise reduction + semantic VAD/transcription latency blow-up (P3, pre-GA).** [thread 1256390](https://community.openai.com/t/realtime-api-with-noise-reduction-has-sudden-increase-of-latency/1256390).
9. **Excess client-side buffering of caller audio (P3).** One author reported buffering "several seconds of user audio before sending it to STT" added "1–2 seconds of latency"; fix was streaming "20ms or 40ms" chunks; claims 250 ms avg / 320 ms P95 over 100 calls but "asserted rather than measured" (Node.js, Whisper+TTS-1, not Realtime). — [dev.to "How I slashed... latency to 250ms" [3P, asserted]](https://dev.to/umair24171/how-i-slashed-ai-agent-phone-calls-twilio-latency-to-250ms-16af)
10. **Session cap.** 60-minute hard limit on a Realtime session. — [OpenAI conversations guide [DOC]](https://developers.openai.com/api/docs/guides/realtime-conversations)
11. **Resampler state artifacts (only if you resample).** Pipecat added `resampler_clear_after_secs` (default 0.2 s) to all telephony serializers "to prevent audio artifacts" from stale resampler history after inactivity. — [Pipecat Twilio serializer docs [DOC]](https://docs.pipecat.ai/api-reference/server/services/serializers/twilio.md); [Pipecat v1.5.0 release notes [DOC]](https://newreleases.io/project/github/pipecat-ai/pipecat/release/v1.5.0)

### Inferences
- Prioritized in-house checklist (each item maps to evidence above):
  1. Replace "forward delta immediately" with queue → 20 ms deadline-scheduled sender (monotonic clock, catch-up on stall, reset on `clear`); add ~100–200 ms pre-roll per response. Verify with an inter-frame-interval histogram (target mean 20.0 ms, zero intervals > 40 ms).
  2. On `input_audio_buffer.speech_started`: flush local queue, send Twilio `clear`, send `conversation.item.truncate` with `audio_end_ms` = *frames actually sent at real-time pace* (or last `mark`-acknowledged offset), and `response.cancel` if a response is still generating. Do this unconditionally, including after `response.done`.
  3. Send a `mark` at least once per response (or every 1 s of audio) and log the echo delay; a growing echo delay means you are outrunning real time.
  4. Keep the bridge in the same region as the Twilio processing region (US1 by default; IE1/AU1 if configured) and terminate TLS close to Twilio; measure with Voice Insights jitter (>30 ms is Twilio's ITU-T warning line, see KQ4).
  5. Tune VAD for PSTN: higher `threshold` (LiveKit's example: 0.7), longer `silence_duration_ms`, consider `far_field` noise reduction — but be aware of the pre-GA noise-reduction+semantic_vad latency report and retest on GA.
  6. If artifacts persist with a correct pacer, capture the OpenAI event log (delta counts vs `response.output_audio.done`) to distinguish server-side drops from bridge bugs.
- Event-loop blocking (sync DB/HTTP calls, heavy logging, GC) is a plausible contributor — a 20 ms sender can only hold cadence if the loop is free — but no thread in this research measured it directly on a Twilio+Realtime bridge; the OpenClaw drift numbers (event-loop overhead compounding on relative timers) are the closest evidence. Treat as "likely, unmeasured".
- Sending faster than real time also makes any *subsequent* network hiccup inaudible (Twilio has a backlog), which is why some bridges seem fine until barge-in is tested.

### Gaps
- No primary source quantified GC pauses, container CPU throttling, WebSocket ping/pong timeouts, ngrok/tunnel overhead, or Docker networking as causes of choppiness in this specific stack; these remain hypotheses.
- Twilio does not document whether it applies packet-loss concealment on the WebSocket→PSTN leg beyond what OpenClaw observed as "jitter-buffer concealment".
- "Double talk" from acoustic echo: no source found discussing AEC in a Twilio Media Streams bridge (PSTN legs normally have carrier-side echo cancellation; not verified).

## Key question 4 — Diagnosis techniques

### Takeaway
The techniques that actually found root causes in the sources were: per-frame send-interval histograms on the bridge, two-sided recordings aligned in an audio editor to isolate transport delay, PCAP jitter/loss/delta on the SIP leg, and OpenAI event-log accounting (delta count vs `done`). Twilio Voice Insights gives carrier-leg jitter/loss/MOS every 10 s but does not instrument the Media Streams WebSocket leg.

### Cited Findings
- Twilio Voice Insights collects "jitter, packet loss, packet rate" at Twilio's media gateways for carrier/trunking calls, plus MOS/RTT/audio levels for SDK calls; "every second for Voice SDK calls, and every 10 seconds for SIP/Carrier calls (cumulative statistics for the previous 10 seconds)"; graph threshold lines "based on the ITU-T standards for VoIP quality", jitter line at 30 ms. The page does not mention Media Streams/WebSocket measurement. — [Twilio Voice Insights advanced features [DOC]](https://www.twilio.com/docs/voice/voice-insights/advanced-features)
- MOS "takes jitter, latency, and packet loss values as inputs and outputs a number between 1–5"; a score of 4.2+ "is generally considered to be a good quality call" (per Twilio Voice Insights docs as summarized in search results). — [Twilio Voice Insights call metrics [DOC]](https://www.twilio.com/docs/voice/voice-insights/api/call/call-metrics-resource)
- Inter-frame timing histogram: OpenClaw logged mean interval and counts of intervals > 25 ms and > 40 ms before/after the fix (21.896 ms → 20.003 ms; 60/12 → 0). — [openclaw #119070 [ISSUE]](https://github.com/openclaw/openclaw/issues/119070)
- Two-sided recording alignment: "recorded the same call from both Twilio's side and LiveKit's Agent Insights system, then aligned the audio waveforms in Audacity"; subtracting agent processing isolates transport latency (162 ms one-way). — [LiveKit thread 270 [ISSUE]](https://community.livekit.io/t/subject-325ms-one-way-audio-latency-in-sip-inbound-trunk-need-internal-pipeline-diagnostics/270)
- PCAP "jitter, loss and delta" and mixer restart/zero-mix counters to distinguish network from software on self-hosted SIP. — [LiveKit thread 957 [ISSUE]](https://community.livekit.io/t/glitches-crickly-noise-chopping-some-time-voice-goes-away/957)
- OpenAI-side accounting: compare `response.audio.delta` bytes vs `response.audio.done` / token counts to prove server-side drops. — [OpenAI thread 1094267 [ISSUE]](https://community.openai.com/t/websocket-realtime-api-randomly-dropping-audio-packets/1094267)
- `mark` echoes as playout ground truth (Twilio echoes when the marked audio finishes, or immediately if the buffer is empty). — [Twilio WebSocket messages [DOC]](https://www.twilio.com/docs/voice/media-streams/websocket-messages)
- Stream lifecycle errors via `statusCallback` (`StreamEvent`, error details). — [Twilio `<Stream>` [DOC]](https://www.twilio.com/docs/voice/twiml/stream)
- Production latency reality (10M+ minutes tested across LiveKit/Pipecat/ElevenLabs/Retell/Vapi/custom): P50 1.4–1.7 s, P90 3.3–3.8 s, P95 4.3–5.4 s, P99 8.4–15.3 s; target < 800 ms; component budgets STT 200–400 ms, LLM TTFT 300–1000 ms, TTS TTFB 150–500 ms, network 100–300 ms, VAD/turn 200–800 ms. — [Hamming.ai (2026-01-12) [3P]](https://hamming.ai/blog/voice-ai-latency-whats-fast-whats-slow-how-to-fix-it)

### Inferences
- A minimal bridge-side telemetry set that would have caught every root cause in the sources: (a) outbound send-interval histogram per call; (b) outbound backlog seconds (bytes queued / 8000); (c) `mark` round-trip; (d) inbound `chunk` gaps and `timestamp` deltas (caller-side loss/jitter); (e) OpenAI delta count vs `done` per response; (f) event-loop lag sampler (e.g. a 10 ms timer that logs when it fires late).
- Because Voice Insights stops at Twilio's media gateway, "MOS looks fine but audio is choppy" points at the WebSocket leg or the bridge, not the carrier.

### Gaps
- No Twilio document confirms whether Voice Insights exposes anything for the `<Stream>` WebSocket leg; assume it does not.
- I found no published tool that replays a Twilio Media Streams session with timing for offline analysis.

## Key question 5 — How the platforms/frameworks architect the audio path (and whether they'd remove the problem)

### Takeaway

Trade-off: ConversationRelay cannot use OpenAI speech-to-speech (text in/out); OpenAI SIP gives you no audio hook; LiveKit adds a measured ~160 ms transport leg.

The cost is architectural: it is text-in/text-out, so OpenAI Realtime speech-to-speech (and its prosody/latency advantages) cannot be used; you would run a text LLM + Twilio-hosted ElevenLabs/Google/Amazon TTS instead.
- **OpenAI's SIP connector is the cheapest way to keep `gpt-realtime` S2S and drop the bridge**: Twilio Elastic SIP Trunk → OpenAI; the app only sees events and controls (accept/refer/hang up). It removes pacing, truncation and `clear` handling from your code, but you lose raw audio (no recording tap, no custom mixing/background track, no per-frame telemetry) and you depend on OpenAI's GeoIP routing for the media leg.

- **Pipecat** is the closest to "fix in-house with a framework": same Twilio Media Streams transport, but the serializer already sends `clear` on interrupt, handles resampler artifacts, and pins Twilio `region`/`edge`. Whether its output transport paces to real time is not stated on the pages fetched (see Gaps) — verify in `BaseOutputTransport` before relying on it.
- Vapi/Retell/Bland/ElevenLabs solve the same problems behind endpointing/interruption sliders; their Twilio-vs-SIP advice (Vapi) and PSTN-specific defaults (Vapi "office" background on phone calls, Retell BVC, Bland `noise_cancellation` on by default) indicate that phone-audio VAD false positives are a recurring production problem they tune around, not a one-off.
