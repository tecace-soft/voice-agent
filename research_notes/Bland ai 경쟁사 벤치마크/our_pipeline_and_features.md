## A1. Which engine runs a real call, and how Twilio is wired (inbound, outbound, transfer, AMD)

### Takeaway
One FastAPI process (`openai-agent-app`) bridges Twilio Media Streams to OpenAI over two mutually exclusive engines selected by one env var: `OPENAI_LIVE_MODEL` blank → OpenAI **Realtime API** (`bridge.py`, default model `gpt-realtime-2.1`); set (e.g. `gpt-live-1`) → **GPT-Live** (`live_bridge.py`, voice model + `gpt-5.6-terra` tool delegate). Every recent audio fix and the dashboard-prompt integration exist only in the GPT-Live bridge, which strongly implies production runs GPT-Live (see Gaps).

## A2. Audio path — OpenAI Realtime bridge (`bridge.py`)

### Takeaway
G.711 μ-law 8 kHz base64 passes straight through in both directions with no resampling, no client-side buffering and no pacing: each Twilio `media` frame becomes one `input_audio_buffer.append`, and each `response.output_audio.delta` becomes one Twilio `media` message. Barge-in on `input_audio_buffer.speech_started` sends Twilio `clear` and `response.cancel`, but never `conversation.item.truncate`. Turn detection is `semantic_vad` (eagerness `medium`) by default with a runtime fallback to `server_vad` (threshold 0.8, prefix 300 ms, silence 700 ms).

### Cited Findings
- Module doc: "Both sides speak G.711 μ-law, so audio bytes pass straight through (base64) with no conversion" — [bridge.py:1-10](openai-agent-app/src/openai_agent/realtime/bridge.py#L1-L10). OpenAI connection: `wss://api.openai.com/v1/realtime?model={model}` via `websockets.connect` with a Bearer header — [bridge.py:40,51-60](openai-agent-app/src/openai_agent/realtime/bridge.py#L40-L60).
- The OpenAI socket is opened as a task **before** waiting for Twilio's `start` event to overlap the handshakes — [bridge.py:110-117](openai-agent-app/src/openai_agent/realtime/bridge.py#L110-L117). On an inbound call the bridge then `await`s `fetch_business_config` (an HTTPS round trip unless cached) before it can send `session.update` — [bridge.py:158](openai-agent-app/src/openai_agent/realtime/bridge.py#L158).

- Without `conversation.item.truncate`, the model's context keeps text the caller never heard after a barge-in, so later turns may reference "what I just said" — a coherence issue, not an audio one.
- Because every `speech_started` flushes Twilio's buffer, any false VAD trigger (room noise, the caller's own echo) cuts the agent mid-word on this engine; the code comments about speakerphones ([settings.py:181-187](openai-agent-app/src/openai_agent/config/settings.py#L181-L187)) show this was observed.

## A3. Audio path — GPT-Live bridge (`live_bridge.py`): reservoir buffering, pacing, barge-in, pre-rendered greeting

### Takeaway
The GPT-Live bridge is where all the "stutter" work went. Model audio is not forwarded directly: it is decoded into an in-process byte reservoir and a dedicated sender task feeds Twilio in 100 ms chunks, keeping Twilio ≤0.6 s ahead of playback and holding the first 0.5 s of each turn as a cushion, because "GPT-Live does not send at a steady rate: it bursts, then stalls — measured at up to 576ms of nothing in the middle of a sentence". Barge-in is driven by the caller's *transcript* events, drops everything held beyond 150 ms, and only ever `clear`s Twilio's own buffer during the pre-rendered greeting; the module itself says whether Twilio's buffer should be cleared on interruption is "UNVERIFIED on a real call". Greeting audio is pre-rendered via the TTS API, low-passed and decimated to 8 kHz μ-law in Python, and cached per process.

### Cited Findings
- Design differences vs Realtime, in the module docstring: no `response.done` (hang-up waits for audio to go quiet), no per-response instructions (uses `session.instructions.append`), "No `response.cancel` / `speech_started`. GPT-Live is full duplex and handles barge-in itself", audio the model must not hear is replaced with μ-law silence "because GPT-Live expects input audio to keep flowing", tool calls arrive wrapped in `response.event`, transcripts are timed fragments — [live_bridge.py:1-24](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L1-L24). Line 20-23: "UNVERIFIED on a real call: whether Twilio's playback buffer outlives an interruption. Twilio's own GPT-Live sample never clears it. The call-end log reports how far audio ran ahead of playback; if that is seconds rather than a fraction of one, callers will hear the agent keep talking after they cut in."
- `session.start` payload: `session.model = OPENAI_LIVE_MODEL`, `instructions` (voice prompt + optional "# RIGHT NOW" greet-now block), `audio.format {type: "audio/pcmu", rate: 8000}`, `audio.output.voice`, `delegation {type: "responses", responses: {model: OPENAI_LIVE_BACKEND_MODEL, instructions, tools (strict:false), tool_choice: "auto", parallel_tool_calls: false, reasoning: {effort: "low"}}}` — [live_session.py:155-185](openai-agent-app/src/openai_agent/realtime/live_session.py#L155-L185); endpoint `wss://api.openai.com/v1/live/sessions` — [live_session.py:19](openai-agent-app/src/openai_agent/realtime/live_session.py#L19). "There is no turn-detection or transcription config to send — GPT-Live decides when to speak itself" — [live_session.py:9-11](openai-agent-app/src/openai_agent/realtime/live_session.py#L9-L11).
- **Reservoir rationale** (comments): "Measured on a real call: ten gaps, four seconds in total, with the lead never above 0.1s" and "GPT-Live does not send at a steady rate: it bursts, then stalls — measured at up to 576ms of nothing in the middle of a sentence, with this process idle throughout. Forwarding each chunk the moment it arrives passes those stalls straight to the caller, which is the stutter." The earlier silence-injection fix "is both too late and actively worse" — [live_bridge.py:129-148](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L129-L148).
- Tunables: `_AUDIO_PRIME_SECONDS = 0.5`, `_AUDIO_PRIME_PATIENCE = 0.15`, `_AUDIO_TURN_GAP = 1.0`, `_AUDIO_LEAD_SECONDS = 0.6`, `_AUDIO_SEND_CHUNK = 0.1`, `_AUDIO_INTERRUPT_KEEP = 0.15`, `_UNDERRUN_SECONDS = 0.06`, `_LOOP_LAG_SECONDS = 0.08`, `_MAX_HELD_FRAMES = 150` (3 s of 20 ms frames) — [live_bridge.py:91,107,149-170](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L91-L170).
- **Model → reservoir**: on `session.output_audio.delta` the bridge skips if closing, skips while the pre-rendered greeting owns the line (`greeting_until`), accounts the chunk, then `state["out"].extend(base64.b64decode(payload))` — "Into the reservoir, and no further: `_stream_to_caller` is the ONLY thing that writes audio to Twilio. Sending from here as well delivered every chunk twice … which is what a caller hears as the agent stuttering and repeating itself" — [live_bridge.py:769-790](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L769-L790).
- **Sender** `_stream_to_caller`: while not closing: if reservoir empty → re-arm priming only if >1.0 s since the last delta, sleep 10 ms; when priming (and not hanging up/transferring) wait until ≥0.5 s is held or 0.15 s has passed since the last delta; if Twilio already has ≥0.6 s queued (`play_until − now`) sleep min(excess+10 ms, 50 ms); else send `step = 800` bytes (100 ms) as one base64 `media` message and advance `play_until` — [live_bridge.py:1040-1093](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L1040-L1093). GPT-Live "streams output audio CONTINUOUSLY — silence included", so "is the agent talking?" decisions look at samples (`_has_sound`: ≥2 % of μ-law bytes in segment ≥3) — [live_bridge.py:882-895](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L882-L895).
- **Underrun diagnostics**: a chunk arriving mid-turn (<1.0 s since last delta) when Twilio has run out (`now − play_until > 0.06`) and the reservoir is empty counts as an underrun; first five logged "agent audio ran dry for %.0fms — the caller heard a gap" — [live_bridge.py:909-933](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L909-L933). `_note_delta_gap` tracks the longest intra-turn gap from OpenAI — [live_bridge.py:898-906](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L898-L906). `_watch_the_clock` sleeps 50 ms in a loop and records how late each wake-up was (>80 ms = "this process was blocked") — [live_bridge.py:1096-1111](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L1096-L1111). At call end it logs max playback lead, underrun count/seconds, and "the stalls are upstream" vs "THIS PROCESS was blocked; that is ours to fix" — [live_bridge.py:1725-1744](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L1725-L1744).
- **Caller → model**: `_caller_to_live` forwards each Twilio `media` payload as `{"type": "session.input_audio.append", "audio": payload}`; if `_not_the_caller()` (inbound before greeting, forward guard, or leaving voicemail) the payload is replaced by same-length μ-law silence (`0xFF`); frames arriving before `session.started` are held (max 150) and flushed — [live_bridge.py:672-752](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L672-L752).

### Inferences
- The end-to-end added latency of this design is ~0.5 s (prime) + up to 0.6 s (lead) at each agent turn start, on top of GPT-Live's ~2.5 s cold first-word; the pre-rendered greeting hides it only for the opening line.

## A7. Candidate root causes for intermittent choppy / cut-out audio, ranked

### Takeaway
The code itself documents that GPT-Live's output arrives in bursts with stalls up to ~576 ms and that the process was idle during them; the 0.5 s prime + 0.6 s lead reservoir covers stalls up to roughly a second but not longer ones. Beyond that upstream cause, the most likely code-level contributors are (1) the reservoir being emptied on *any* caller transcript fragment, (2) audio dropped while the pre-rendered greeting "owns the line", (3) mid-call instruction appends that make the model abandon a sentence, and (4) event-loop contention in the single worker.

### Cited Findings (evidence for each candidate)
1. **Upstream GPT-Live stalls exceeding the buffer** — stated measurements: "ten gaps, four seconds in total" and "up to 576ms of nothing in the middle of a sentence, with this process idle throughout" — [live_bridge.py:129-148](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L129-L148); the reservoir keeps only 0.6 s at Twilio and primes 0.5 s — [live_bridge.py:149-157](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L149-L157); the underrun logger exists precisely for this — [live_bridge.py:921-933](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L921-L933). The GPT-Live session also closes on OpenAI's side sometimes ("it went dead mid-sentence") — [live_bridge.py:866-879](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L866-L879).
2. **Reservoir dropped on every caller transcript fragment** — `_caller_started_talking` runs on each `session.input_transcript.delta` and deletes all held audio beyond 150 ms before checking anything else — [live_bridge.py:809,1020-1024](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L1009-L1024); GPT-Live delivers whole answers far ahead of playback ("a fifteen-second answer can land in about a second") — [live_bridge.py:1578-1580](openai-agent-app/src/openai_agent/realtime/live_bridge.py#L1575-L1589). - **#7 (medium, Realtime only)**; **#8, #9, #10 (low / opening-only)**.
- Things that are *not* the problem in code: chunk size (Twilio accepts any size and buffers), base64 handling (passthrough), manual `commit` (never sent), synchronous DB/HTTP on the loop (all async or threaded), `session.update` size mid-call on GPT-Live (appends are small).

## B4. Voicemail transcription pipeline (`transcribe-app`) and what the dashboard shows

### Takeaway
A separate Python batch poller reads voicemail audio attachments over IMAP, transcribes + extracts fields in one Gemini multimodal call, appends a row per voicemail to the customer's Google Sheet (with an "Open email" deep link, never storing audio), and reports each run to `transcribe-backend`, which the dashboard shows as run/analytics screens per mailbox. The same app also writes messages the phone agent took into the sheet.

### Cited Findings
- Pipeline: "IMAP inbox ──▶ audio attachments ──▶ Gemini: transcript + fields ──▶ Google Sheet row"; fields: caller name / phone / requested time / summary; idempotent via `.processed.json`; "The recording is never stored or served by us" — [transcribe-app/README.md:1-12,57-77](transcribe-app/README.md#L57-L77).
- Run reporting to `<BACKEND_URL>/transcribe/runs` with the mailbox address, which the dashboard uses to attribute data per account — [transcribe-app/README.md:48-55](transcribe-app/README.md#L48-L55); backend routes under `/transcribe` — [transcribe.ts:61-205](transcribe-backend/src/routes/transcribe.ts#L61-L205).
- Sheet hand-off for agent messages: `GET /calls/awaiting-sheet` + `POST /calls/:id/sheet-written` (shared key) — [calls.ts:93-122](transcribe-backend/src/routes/calls.ts#L93-L122); run as the `messages` container next to the agent — [docker-compose.yml:51-81](openai-agent-app/docker-compose.yml#L51-L81).

### Inferences
- "Answered calls" was deliberately shaped like a transcribed voicemail so both pipelines read the same to a customer — [inboundCalls.ts:4-8](transcribe-backend/src/db/inboundCalls.ts#L4-L8).

## B5. Demos section: prospects/CRM, test call, research, post-call review
